# sce_app_docs 架构重构方案：静态构建 + 内嵌 HTTP 服务

> 日期：2026-09-29 ｜ 状态：待评审（未动手）
> 前置结论：用户已接受「md 更新 → 约 7 秒后可见」的重建延迟，放弃 HMR 实时性。

## 1. 背景：现有架构的病灶

### 当前形态

```
docs.exe（egui GUI/CLI）
  └─ spawn 外部长寿进程：node（Volta shim）→ cmd.exe /C → 真 node.exe → vitepress dev server
```

exe 只是「遥控器」，真正的 HTTP 服务是外部 node 进程树。

### 已暴露的问题清单（v0.1.0 ~ v0.1.7 全部病史）

| # | 问题 | 当时修法 | 性质 |
|---|------|---------|------|
| 1 | cmd 壳 spawn node 后自退，杀壳杀不到 node → 孤儿占端口 | 改直接 spawn node.exe | 补丁 |
| 2 | node 实为 Volta shim，内部又开 cmd → 壳回来了 | 未修（taskkill /T 碰巧能级联） | 带病运行 |
| 3 | 关 app 不杀服务 → 孤儿 | 未修 | 架构缺陷 |
| 4 | 重开 app 后 child 句柄丢失，stop() 空操作，还顺手删了 PID 文件（自毁兜底） | 未修 | 架构缺陷 |
| 5 | 无 strictPort，端口被占静默漂移到 18754，UI/Cloudflare 仍指 18753 | 未修 | 架构缺陷 |
| 6 | vitepress 只监听 IPv6 → 端口探测误判死 | 双栈探测 | 补丁 |
| 7 | Cloudflare 切项目白屏（入口 script 无 hash + HMR 不可用） | transformIndexHtml 加 hash + 关 hmr/ws | 补丁（已稳定） |
| 8 | 一刀切 no-cache 拖慢加载 | 删掉恢复 immutable | 补丁 |

**病根**：跨进程管理一个「长寿、多层壳、端口会漂移」的外部进程树。Windows 没有可靠的父子生命周期绑定（除非用 Job Object），句柄/PID 文件/端口探测全是间接证据，任一环节断裂就漂移。

### 联调为什么没发现

v0.1.6/0.1.7 联调只覆盖了「同进程内起停」（CLI serve）和「手动 spawn/kill」（绕过 app），**从未覆盖跨 app 重启的生命周期**——问题 3/4/5 全在这个盲区里。

## 2. 方案选型

### 候选 A：保留 dev server + Job Object 托管（补丁的极限）

用 Windows Job Object（`KILL_ON_JOB_CLOSE`）包住 spawn，父死子灭由 OS 保证；stop 改按端口找主杀；恢复 strictPort。

- 优点：改动最小，保留 dev server「改 md 刷新即见」
- 缺点：**仍是外部长寿进程树**。句柄丢失、shim 壳、端口漂移这些类别的问题只是被压制，不是消失。「头疼医头」的感觉会持续

### 候选 B：exe + bun

bun 是单一真二进制，消掉 shim/cmd 壳。

- 优点：进程树变一层
- 缺点：仍是外部长寿进程（候选 A 的病都在）；vitepress 2.0-alpha + vite 8(rolldown) 在 bun 运行时下兼容性无担保；引入新工具链风险。**换汤不换药，否决**

### 候选 C（推荐）：静态构建 + exe 内嵌 HTTP 服务

```
docs.exe
  ├─ 内嵌 axum HTTP 服务（端口由 exe 自己持有）
  ├─ 文件监听（notify crate，debounce ~1s）→ 触发重建
  └─ node 只在「构建」时短命 spawn：vitepress build → 5 秒 → 自己退出
       （再套 Job Object 双保险，即使残留也会自行退出）
```

**实测数据**（2026-09-29，The_Shadow_of_Return 全量文档）：`vitepress build` 总耗时 **5.5s**，产物 **5.2MB**。

- 停止 = 关 listener；切项目 = 重建换内容；关 app = 端口随进程消失。**「孤儿」这个类别直接消失**
- 搜索索引构建期生成，重建即更新（与 dev 模式能力对齐）

**代价**：md 保存 → debounce(1s) + build(5.5s) ≈ **7 秒后刷新可见**（已获用户确认接受）。无 HMR 自动刷新（现状本就如此）。

### 决策：候选 C

## 3. 目标架构设计

### 模块拆分（src/ 现状 ~1300 行重构为）

```
src/
  main.rs              # 入口：CLI 分发（serve）→ appsdk app::run；App 状态；ShellApp 壳
  core/
    config.rs          # GlobalConfig/ProjectConfig（沿用，新增字段见 §4）
    site.rs            # 站点生成：junction 聚合 + config.mjs/主题/index.md（从 server.rs 拆出，逻辑不变）
    builder.rs         # 构建管线：spawn node vitepress build（Job Object 包裹）→ dist；构建队列（防抖合并）
    watcher.rs         # notify 监听源目录 → debounce → 投递构建事件
    server.rs          # 内嵌 axum 静态服务：serve dist，端口生命周期与 exe 一致
  ui/
    main_page.rs       # 主页（启停按钮、状态、打开浏览器）
    settings.rs        # 设置页（端口/局域网/域名白名单开关，沿用）
doc/research/          # 本文档
```

### 关键机制

**端口与启停**
- 启动：axum bind 配置端口；**被占 = 直接报错提示**（等效 strictPort，天然没有漂移）
- 停止/切项目/关 app：drop listener 即释放，无外部进程可残留
- 双栈：绑 `0.0.0.0`（局域网开）或 `127.0.0.1`（关）；IPv6 由 axum 双栈 socket 处理，不再依赖 vitepress 行为

**构建管线（builder.rs）**
- 触发源：启动服务、md 文件变更（watcher）、手动「重建」按钮
- 防抖：变更后 1s 内聚合，构建期间新变更排队一次（不堆积）
- spawn：`node vitepress build <site>`，Job Object（`KILL_ON_JOB_CLOSE`）包裹；构建输出进 dev-server.log 同款日志
- 原子切换：build 到 `dist.new` → 成功后 rename 替换 `dist`（失败不影响线上旧内容）
- 构建期 axum 继续服务旧 dist，**重建过程不掉线**

**Cloudflare 兼容（保留 v0.1.6/0.1.7 成果）**
- 静态产物天然带 hash 文件名（`assets/*.[hash].js`），immutable 缓存安全，**白屏问题在构建模式下不复存在**（vitepress build 的 HTML 引用 hash 资源）
- 域名白名单开关：axum 层校验 Host 头（替代 vite allowedHosts）
- transformIndexHtml/hmr/ws 那套 vite.config.js 全部删除（不再需要）

**CLI serve 契约（沿用并增强）**
```
sce_app_docs serve --project-path <项目根> [--port N] [--timeout S] [--lan] [--allowed-hosts H]
```
- 语义调整：serve 现在前台常驻（服务在进程内），Ctrl+C 即停——端到端自测就是真实代码路径
- 自测脚本断言：起→端口通→HTTP 200→停→端口释放，全生命周期自动化

### 配置变更（GlobalConfig）

| 字段 | 变化 |
|------|------|
| `port` / `lan_access` / `allowed_hosts` / `allowed_hosts_enabled` | 沿用 |
| `node_path` | 沿用（构建期用） |
| 新增 `auto_rebuild: bool`（默认 true） | 关则只手动重建（浏览场景省 CPU） |

### vitepress 配置调整

- `ignoreDeadLinks: true` 写入生成的 config.mjs（实测 build 被 4 个死链拦截；文档聚合场景死链是常态）
- dev 专用配置（vite.config.js 三件套）废弃删除

## 4. 性能分析：公网为什么慢（附 Clash 探查结论）

### 实测对照（2026-09-29）

| 路径 | TLS 握手 | 说明 |
|------|---------|------|
| 直连 CF 边缘 | 0.68s | 本机直连 104.21.9.13，快 |
| 走 Clash 代理(7897) | 1.26s | **代理节点额外 +0.6s/连接**，且每 RTT 都加节点延迟 |
| CF→源站（源站关闭时） | 31s 超时 | 「服务关闭后刷新也很慢」的原因：CF 等源站超时，正常表现 |

### 慢的归因排序

1. **主因：dev server 按需编译的未打包 ESM**。首开一页要拉几百个独立模块（vue runtime、vitepress app、逐组件、逐 md），每个请求都过隧道全程 + vite 实时 transform。宝塔 web 是构建好的少量静态资源，请求数差两个数量级
2. **次因：Clash 分流**。浏览器走系统代理时，CF 域名被分到代理节点绕路。缓解：Clash 加规则 `DOMAIN-SUFFIX,codeye.games,DIRECT`（CF 边缘直连本来就快）
3. **排除项**：192.168.31.10 vs localhost 绑定差异、node 本身开销——微乎其微

### 静态化后的预期

一个页面 = HTML + 几个 hash 命名打包 chunk（immutable 强缓存），请求数从几百降到个位数；CF 边缘可缓存静态资源，二次访问接近秒开。**隧道场景质变。**

## 5. 迁移步骤

1. `core/site.rs`：从 server.rs 拆出站点生成逻辑（junction/config.mjs/主题/index.md），加 `ignoreDeadLinks`
2. `core/builder.rs`：构建管线 + Job Object + 构建队列
3. `core/server.rs`：推倒重写为 axum 内嵌服务（含 Host 白名单校验）
4. `core/watcher.rs`：notify 监听 + debounce
5. main.rs/CLI/GUI 接线（启停按钮语义不变；状态机简化为 Idle/Building/Serving/Failed）
6. 全生命周期自测（见 §6）通过后删旧代码（child/PID 文件/kill_orphan/wait_port_free/vite.config.js 生成）

## 6. 验收标准（自动化自测，不靠手点）

| 场景 | 断言 |
|------|------|
| 起服务 | 端口监听 + HTTP 200 + 页面标题正确 |
| 停服务 | 端口完全释放（双栈） |
| 改 md | 重建完成后刷新页面含新内容 |
| 搜索 | 新内容可被 local search 命中 |
| 切项目 A→B→A | 每次端口内容对应正确项目，无残留 |
| 关 app（服务运行中） | 进程退出后端口立即释放 |
| 重开 app | 状态干净，可正常起停 |
| 端口被外部占用时起服务 | 明确报错，不静默换端口 |
| Cloudflare 访问 | 首开 < 3s（静态化后重测基线） |

## 7. 风险与开放问题

- **构建耗时随文档增长**：当前 5.5s，文档量翻倍后需复测；超过 15s 考虑增量方案（vitepress 无官方增量构建，可退候选 A 混合模式）
- **axum 引入新依赖**：egui 应用加 tokio/axum，编译时间增加；可用更轻的 tiny_http 降低依赖
- **watcher 监听 junction**：notify 对 Windows junction 的递归监听需实测（若漏报，fallback 轮询 mtime）
