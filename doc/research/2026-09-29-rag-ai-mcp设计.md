## 1. 闭环目标

```
代码开发 ──bgd_sce_tools 构建──> .bgd/doc/api_generated（API 文档）
AI/作者讨论 ──沉淀──> .bgd/doc/requirements + .bgd/doc/research（设计/答疑/实测）
        ↓
sce_app_docs 聚合 → 文档站（已有）+ 向量知识库（新增）
        ↓
浏览器 AI 问答（/api/ask）+ IDE MCP 端点（/mcp）
        ↓
AI 开发时检索项目知识 → 产出新代码/文档 → 回到起点
```

## 2. 技术选型（效果优先，零外部服务依赖）

| 环节 | 方案 | 理由 |
|------|------|------|
| Embedding | **本地 fastembed-rs（进程内 ONNX 推理，BAAI/bge-m3）** | 零外部依赖零费用；配置只留 LLM chat API；bge-m3 中文效果好。已确认 fastembed 5.x/6.x 原生支持（`EmbeddingModel::BGEM3`）。本机配置（Ryzen AI MAX+ 395 / 96GB）跑全量模型无压力，不用量化妥协 |
| Rerank | **本地 fastembed TextRerank（BAAI/bge-reranker-v2-m3）** | 检索 top-k 后交叉编码重排再放行——召回质量的关键增强点，本地零成本，默认开（AI 页可关） |
| LLM | 用户中转站 `/v1/chat/completions`（流式 SSE） | 用户已有；只配这一项 |
| 向量存储 | **本地 SQLite（rusqlite）+ 内存暴力余弦** | 文档量小（几百 md → 几千 chunk），暴力检索 <10ms；不引入向量数据库服务；库文件随项目存 `vitepress_home/kb/<站点名>.sqlite` |
| 增量索引 | 按文件内容 hash：重建/变更时只重嵌变更文件 | 本地 embedding 零成本，挂在 watcher 重建管线后自动增量，索引永远跟着文档走 |
| 问答协议 | **多轮 Tool Calling 循环（agentic RAG，见 §4.1；轮数界面可配，默认 5）** | LLM 自主决定再检索/深读全文，效果上限远高于单轮拼 context |
| MCP | **httpd 暴露 `/mcp`（Streamable HTTP 完整实现：session 管理 + SSE 流式响应，JSON-RPC）** | Trae/其他 MCP 客户端直连 `http://localhost:18753/mcp`；无需独立进程 |

**关键原则**：延续 v0.2 架构——一切能力内嵌 exe，不引入任何外部常驻服务。中转站是唯一外部依赖（用户已有，且只用于 LLM chat）。

## 3. 数据管线

```
md 文件（junction 聚合后的站点目录）
  → 分块（按标题层级切，~500 字/块，10% 重叠；保留元数据：文件路径/标题链/URL）
  → 文件 hash 对比 sqlite 已有记录 → 只 embed 变更块
  → 写入 sqlite（chunks 表：id/file/heading/text/embedding BLOB）
  → 检索时全量载入内存（启动一次 + 索引更新后失效重载）
```

- 触发时机：服务启动构建完成后 + watcher 重建完成后（索引跟随 dist 原子翻转一起切换）
- 源 URL 映射：chunk 的文件路径 → 文档站 URL（`/api/libs/common/json` 形式），回答的出处链接可直接点击跳转

## 4. API 设计（httpd 新增路由）

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/search?q=...&k=5` | GET | 纯语义检索，返回 [{text, url, score}]（问答面板/调试用） |
| `/api/ask` | POST SSE | RAG 问答：{question, history} → 流式返回 {think}/{delta}/{tool_call}/{sources}/done |
| `/api/index_status` | GET | 索引进度：{state: idle/indexing/ready/failed, done, total, error}（UI 轮询） |
| `/mcp` | POST | MCP Streamable HTTP：initialize / tools/list / tools/call（含 session 管理 + SSE 流式响应，完整实现） |

### 4.1 多轮 Tool Calling 问答（效果增强核心）

单轮「检索→拼 context→回答」的局限：查询词不准就检索不到、问题跨多文档时一轮 context 装不下。改多轮循环，LLM 当司机：

```
用户问题（带会话历史）
  → 第 1 轮：LLM 收到问题 + 工具定义（search_docs/get_doc/list_sources）
  → LLM 返回 tool_call（如 search_docs("sql_toolkit 事务")）
  → 本地执行检索，结果塞回 messages
  → 第 2 轮：LLM 看结果，不够就再 tool_call（换关键词/深读 get_doc 全文），够了就流式输出回答
  → 循环上限由界面配置（默认 5，范围 1-20，防死循环），每轮工具调用实时推给前端展示（「正在查 sql_toolkit.md…」）
```

与 MCP 工具集**同一份实现**（对内 tool call 和对外 MCP 共用检索/取文档函数），不重复造。检索命中后先过 **reranker 重排**再塞给 LLM。回答末尾附出处链接。

**前端面板同步展示思考/工具调用过程**（折叠面板，参考薄荷输入法方案）：`think`（思考链）/`tool_call`（查了哪个库什么关键词）/`delta`（正文）分事件推送。

**MCP 工具集**：
- `search_docs(query, top_k)` — 语义检索项目文档，返回文本块 + 出处
- `get_doc(path)` — 按路径取文档全文（检索到后深读用）
- `list_sources()` — 列出当前聚合的文档源（让 AI 知道库里有什么）

## 5. 前端（VitePress 主题）

## 6. 设置页与菜单

菜单变为：**主页、全局、项目、AI、MCP、帮助**

- **AI 页**：LLM chat 配置（base_url / api_key / model + 连通测试按钮）；最大工具调用轮数（默认 5，范围 1-20）；rerank 开关（默认开）；**模型管理**（embedding/reranker 模型状态 + 下载链接展示 + 「导入本地模型」按钮——用户可先手动下载好再导入，也可走镜像在线下载）；索引进度与状态（见 §6.1）
- **MCP 页**：MCP 端点开关 + 端点地址展示（复制按钮）+ 已暴露工具列表说明
- **帮助页**：使用说明（怎么配中转站、MCP 怎么接 Trae、CLI 用法）

### 6.1 索引状态与不阻塞（硬要求）

- **全程后台线程**：embedding 索引构建/增量更新不阻塞 UI 与文档站（服务照常、问答照常用旧索引）
- **状态可见**：主页与 AI 页显示索引状态条——`索引中 128/456 chunks（3.2 chunks/s）` / `就绪（456 chunks，最后更新 xx:xx）` / `失败：原因`；进度经 `/api/index_status` 暴露，GUI 轮询渲染
- **模型下载带进度且充分利用带宽**：在线下载走 `HF_ENDPOINT=https://hf-mirror.com` 镜像（fastembed 原生支持），也可用本机 clash 代理（`HTTPS_PROXY`）；同时提供「导入本地模型」——用户手动下载（千兆网/多线程下载器随便造）后界面选目录导入
- 索引失败不影响文档站本体（降级为无问答，错误可见）

### 6.2 安全边界（硬约束）

**检索工具只读，无任何系统操作能力**：
- 三个工具（search_docs/get_doc/list_sources）全部是**只读文档库**——没有 shell 执行、没有写文件、没有网络访问（除 LLM API 本身）
- `get_doc(path)` 路径严格限制在当前聚合的文档源目录内（防 `../../D:/` 路径穿越）
- 问答里发「查找我 D 盘」这类指令，最多只能在文档库里检索「D 盘」这个词——**摸不到文件系统**
- MCP 端点同理（对外暴露的就是这三个只读工具）
